Sticky Policies

A demo using ODRL, DPV and N3 reasoning

From the ODRL-FORCE team at KNoWS UGent

When we share data, how do we keep track of what people are allowed to do with it?

Imagine a research dataspace: a hospital, a university and a partner lab share data while remaining responsible for their own systems. A sticky policy carries the hospital’s conditions across those organisational boundaries. Change a request to see whether the rules support it — and why.

    What travels with the data?

    The trust envelope is a TriG dataset. A blank node names the graph containing the actual data, and the policy refers to that same node. The example includes three invented observations so you can inspect the payload as well as its conditions. 

    # The same blank node names and describes the data graph.
_:data { :sample-1 :value 12.4 . }
_:data :stickyPolicy :policy-b .
_:context {
  :offered-use odrl:target _:data .
}

    At each dataspace handoff, the recipient gets the payload, policy, evidence and proof together. Blank node labels are local to the dataset; a fresh use still needs a fresh decision.

    What does this demo use from FORCE?

    The N3 program evaluates one policy and a sotw:EvaluationRequest against a declared sotw:SotW snapshot. It derives a report:PolicyReport, a report:PermissionReport and nine premise reports for target, action, party and the six constraints. The interface reads those RDF report states directly.

    All premises must be Satisfied for Active. An Unsatisfied premise makes the permission Inactive. The current snapshot supplies explicit negative evidence; missing information without a declared status is left unreported. A matching request is Attempted. There are no action observations, so performance is Unknown and the deontic state is NonSet. The future onward-sharing duty is not evaluated.

    This is a documented FORCE-based subset for this research profile, not a general FORCE evaluator. Agreement construction is a separate demo rule, not the full agreement-instantiation algorithm. See FORCE, its compliance report vocabulary and contextual input model.

    How does the TriG envelope refer to its data?

    In TriG, the same blank node can label a graph and occur in triples about that graph. Here, _:data labels the payload graph; the ODRL targets and DPV evidence use that same node in the context graph. The catalogue identifier :cohort-b points to it.

    The exact N3 rules and proof are also included as text artifacts, since N3 formulae are not native TriG syntax. The verifier checks the payload and context as RDF graphs, then replays the saved proof. Renaming blank-node labels does not change that RDF structure. See the W3C TriG graph syntax.

    Where would this fit in a real dataspace?

    The N3 reasoner could serve as a policy decision component alongside a connector. The provider publishes an offer; a consumer proposes a use with evidence; the rules derive an agreement when the conditions are supported. The connector and the participant’s applications would then need to act on that result.

    This demo does not implement a catalogue, participant identity, credential verification, contract-negotiation or transfer protocols, or runtime usage control. A checked proof explains a decision; it does not itself make a connector enforce the policy. The trust envelope is an illustrative bundle, not a standard dataspace message.

    For background, see IDSA’s Dataspace Connector usage-control documentation ↗. This demo is not an integration with that connector.

    What does the proof establish?

    It establishes that the conclusion follows from these supplied facts and this application’s rules. It does not authenticate the hospital, validate consent in the real world, or enforce deletion. Here, evidence is illustrative, consent is simplified to a cohort-level assertion, and the envelope is unsigned. A production trust envelope would also need trusted issuers, authenticated evidence, freshness checks and enforcement at each recipient.

    De-identification does not mean anonymity. A missing agreement means permission was not established under this profile; it is not a derived prohibition. The retention and policy-carrying terms are local extensions, not a general ODRL evaluator.
